1. PROJECT OVERVIEW
--------------------------------------------------------------------------------
- What the app does:
  LocalGo Services is a local home-service booking marketplace where customers
  discover nearby service professionals using geolocation and map search, book
  doorstep appointments for specific time slots, track live job progress via a
  single-OTP arrival flow, and leave ratings/reviews after completion. Providers
  manage their duty status (Online/Offline with active session heartbeats),
  accept or reject requests, execute jobs step-by-step, and track realized
  earnings, while administrators verify providers and monitor platform activity.

- Users / Roles (backend/src/main/java/com/localgo/enums/Role.java):
  1. CUSTOMER (customer-app)
  2. PROVIDER (provider-app)
  3. ADMIN (admin-app)

- Platform & Tech Stack:
  - Platform: Responsive Web only (3 separate Vite SPAs + legacy monolithic
    frontend/). Native Android / iOS apps: Not implemented.
  - Frontend: React ^18.3.1, Vite ^5.3.1, React Router DOM ^6.23.1,
    Tailwind CSS ^3.4.4, Axios ^1.7.2, Lucide icons, react-hot-toast, and
    Recharts (earnings/revenue charts in provider-app and admin-app).
  - Backend: Java 21 LTS, Spring Boot 3.2.5 (Web, Security, Validation,
    JavaMail), Lombok (backend/pom.xml).
  - Database: Google Cloud Firestore via com.google.firebase:firebase-admin:9.3.0
    (backend) + Firebase Web SDK ^10.12.0 real-time onSnapshot listeners
    (frontends).
  - Hosting / Deployment: Render (https://localgo-services-1.onrender.com/) with
    backend/Dockerfile; Vercel (vercel.json per frontend app;
    https://localgo-services.vercel.app and https://*.vercel.app in CorsConfig).
  - Auth: Firebase Authentication (ID tokens verified by
    FirebaseAuthenticationFilter.java) + custom 6-digit email OTP verification
    and 3-step password reset via AuthController.java and EmailService.java
    (supports Brevo API, Resend API, generic webhook, or Gmail SMTP).
  - Maps: Leaflet ^1.9.4 + react-leaflet ^4.2.1 using OpenStreetMap raster
    tiles (https://{s}.tile.openstreetmap.org/{z}/{x}/{y}.png) and
    ch.hsr:geohash:1.4.0 on the backend. Google Maps / Mapbox SDKs: Not
    implemented.
  - Payments: Cash / UPI radio selector in BookingFlow.jsx only. Payment gateway
    SDK / online checkout (Razorpay / Stripe / UPI intent): Not implemented.

4. BOOKING & PAYMENT FLOW
--------------------------------------------------------------------------------
- Booking Creation & Steps (BookingFlow.jsx & BookingService.java):
  1. Customer selects service category, enters description, preferred date &
     time (HH:mm), doorstep address, and payment method (CASH or UPI).
  2. Backend runs a Firestore transaction querying existing bookings on the same
     providerId and scheduledDate with status in
     [ACCEPTED, ON_THE_WAY, IN_PROGRESS], throwing 409 Conflict
     (BookingConflictException) if time intervals overlap.
  3. Generates a random 4-digit startOtp (1000-9999), sets paymentStatus to
     PENDING, and creates the booking document.

- Status Lifecycle (BookingService.java):
  - REQUESTED   -> ACCEPTED or REJECTED
  - ACCEPTED    -> ON_THE_WAY or CANCELLED
  - ON_THE_WAY  -> ARRIVED, IN_PROGRESS, or CANCELLED
  - ARRIVED     -> IN_PROGRESS (requires valid 4-digit startOtp) or CANCELLED
  - IN_PROGRESS -> COMPLETED (no completion OTP; marks paymentStatus = PAID and
                   syncs completedJobs)

- Pricing Logic:
  Uses provider startingPrice stored in paise (100 paise = 1 INR). Note: if the
  booking request includes amount > 0, BookingService converts it to paise and
  overwrites the provider's price (see Security Issues in Section 10). Dynamic
  quotes, itemized billing, taxes, and platform commissions: Not implemented.

- Payment Integration:
  Not implemented. CASH vs UPI only persists a string label; BookingService
  marks paymentStatus = PAID automatically when the provider sets status to
  COMPLETED.

- Cancellation & Refunds:
  Customers can cancel via PUT /api/bookings/{id}/cancel and providers via
  status update, recording cancelledBy and cancellationReason. Refund handling
  and cancellation fee logic: Not implemented.


5. PROVIDER SIDE
--------------------------------------------------------------------------------
- Registration & Verification:
  Registers via POST /api/auth/register/provider (after email OTP verification)
  and starts with verificationStatus = PENDING. Only VERIFIED providers appear
  in customer discovery (ProviderService.java). Admins approve or reject via
  admin-app.

- Availability (Uber/Rapido-style Duty Model):
  Tracked via available, manualOffline, and lastSeenAt in providers/{id}. Active
  sessions send heartbeats to PUT /api/provider/presence and toggle duty via
  PUT /api/provider/availability. ProviderService only marks a provider Online
  when available == true && manualOffline != true && lastSeenAt is within
  PRESENCE_TIMEOUT_MS = 120,000 ms (2 minutes). Logging out marks offline.

- Accepting / Rejecting / Executing Jobs:
  Incoming REQUESTED jobs appear via Firestore onSnapshot in /requests and can
  be opened (/jobs/:id), accepted, or rejected, then stepped through
  ON_THE_WAY -> ARRIVED -> IN_PROGRESS (4-digit startOtp verification) ->
  COMPLETED.

- Dashboard & Earnings:
  ProviderDashboard.jsx displays live-synced completed jobs count, rating,
  pending count, and realized earnings. ProviderEarnings.jsx sums COMPLETED +
  PAID bookings and displays 7-day / 30-day Recharts trend charts. Payout /
  bank withdrawal workflows: Not implemented.

10. GAPS & PROBLEMS
--------------------------------------------------------------------------------
A. Security Issues:
  1. Missing authorization check in BookingService.cancelBooking(): Any
     authenticated user who knows a bookingId can cancel anyone else's booking
     via PUT /api/bookings/{id}/cancel.
  2. Client-supplied booking price trusted blindly: BookingService overwrites
     the provider's startingPrice whenever request.getAmount() > 0 is sent by
     the client.
  3. Permissive Firestore read rules & OTP leak vector: firestore.rules sets
     providers/{id} to "allow read: if true;" (exposing email/phone publicly)
     and lets both customerId and providerId read full bookings/{id} docs
     (which contain startOtp) directly via Firebase Client SDK.
  4. No rate limiting on OTP endpoints (/api/auth/send-otp, resend-otp,
     forgot-password), allowing email-sending abuse.
  5. Raw exception message disclosure in GlobalExceptionHandler (500 errors
     return ex.getMessage()) and hardcoded fallback demo password (LocalGo@123)
     in application.properties.

B. Bugs & Incomplete Features:
  1. Hidden reviews still appear publicly and count toward provider rating:
     ReviewService.getProviderReviews() and recalculateProviderRating() do not
     filter out reviews where hidden == true.
  2. Booking notifications never trigger: NotificationService.createNotification
     is never called anywhere; only AdminService writes notifications on
     provider verification.
  3. Overlap conflict query excludes ARRIVED status: BookingService checks only
     [ACCEPTED, ON_THE_WAY, IN_PROGRESS], missing ARRIVED.
  4. Favorites have no UI page: Backend GET /api/favorites exists and
     ProviderCard toggles favorites, but customer-app has no /favorites page.
  5. NotificationsPage field mismatch: NotificationDoc writes field "read", but
     NotificationsPage.jsx checks "n.isRead" on Firestore snapshots.
  6. Legacy/duplicate files: Old monolithic frontend/ folder remains in repo;
     provider-app/src/services/ contains unused customer service files;
     README.md documents Admin Service Category CRUD that does not exist.

C. Performance & UX Issues:
  1. Full-collection reads & in-memory sorting/filtering in AdminService,
     ReviewService, and NotificationService without Firestore pagination.
  2. Silent mock fallback in axios.js (getMockResponse) serves stale Bengaluru
     dummy data when Render sleeps or fails instead of clearly surfacing errors.
  3. Native blocking alert() dialogs used in BookingDetailPage.jsx.
  4. No automated frontend unit/E2E test suites (tests exist only for backend
     and Firestore rules) and no CI/CD workflow.

TOP 5 BIGGEST THINGS MISSING FOR A REAL-WORLD MARKETPLACE
--------------------------------------------------------------------------------
1. Real Payment & Refund Gateway (Razorpay / UPI Checkout + Invoices):
   Collect actual online payments, support itemized inspection quotes/extra
   charges, calculate platform commissions, and automate cancellation refunds.

2. Real-Time Live Tracking & Bidirectional Communication (Chat + FCM/SMS):
   Add booking-scoped chat, FCM push/SMS notifications for requests and status
   changes, and live map tracking while the provider is ON_THE_WAY.

3. Real KYC & Document Verification for Providers:
   Support uploading ID/license/trade documents (e.g., via Firebase Storage) so
   admins verify real credentials instead of text descriptions alone.

4. Google Maps / Places Autocomplete & Saved Addresses:
   Replace manual lat/lng and free-text address entry with map pin-dropping,
   address search autocomplete, and saved customer addresses (Home/Work).

5. Production Hardening & Lifecycle Fixes:
   Wire booking notifications, exclude hidden reviews from ratings/display, stop
   trusting client-submitted prices, enforce participant checks on booking
   cancellations, remove silent mock fallbacks, and add OTP rate limiting.
